一台机器上发生的事

你会写代码，也遇到过程序变慢、进程莫名其妙的消失。这一页讲的是机器底下到底发生了什么。
三个场景，每个都先用一个生活里的比喻讲清楚，最后才告诉你它在 Linux 里叫什么。

场 景 一三个工人，四张桌子

你的服务器有 4 个能同时干活的位置（4 核），上面跑了三个服务。
三个服务都想干活，位置只有 4 个。现在由你决定：谁先上？谁最多能占几个？

你刚才其实只做了两件事

第一件：「谁先上」——你调的那个优先级，只在有人抢不到位置的时候才起作用。试试把三个服务的「想干多少」都调小到加起来不到 4，你会发现优先级调到多高都毫无区别：没人在抢的时候，优先级不存在。

第二件：「最多占几个」——这是一个硬上限。不管你优先级多高，碰到它就会被从位置上赶下来，站着等到下一秒。你会看到那个工人被标成「被上限卡住」。

这两件事的「坏法」完全不同，这一点在线上很要命：优先级低只是慢一点，服务还平滑；撞上硬上限是被强制停顿再启动，表现出来是一阵一阵的卡顿。而且这时候你看 CPU 总使用率并不高——因为它是被「掐停」的，不是「忙不过来」。

它们在 Linux 里叫什么

「优先级」= cpu.weight。相对值，只在争抢时按比例分。

「最多占几个」= cpu.max。硬配额，撞上去叫 throttled（被限流）。

这三个工人住在同一个 cgroup 里。Docker 给容器做资源限制，用的就是这个东西——那篇文章说「cgroup 是 docker 的基础」，指的就是这一层。

场 景 二桌子可以排队，这张桌子不行

位置不够的时候，工人排队等一会儿，活最终还是能干完。
现在换一样东西试试：内存。每个服务有一张自己的桌子放材料，你也可以限制桌子的大小。

桌子很小← 拖这条线改变限制 →桌子很大

这就是内存和 CPU 最根本的区别

CPU 不够用的时候，大家排队。慢，但每个人都在往前走，活最终会干完。

内存不够用的时候，没有排队这回事。材料已经堆在那儿了，你要么给它地方，要么把它整个扔掉——不存在「先放一半，等下再放」。

所以超了内存的后果不是「变慢」，是这个进程当场消失。它手里做到一半的事情全部丢掉，然后从头再来一遍。你在监控上看到的现象是服务反复重启，而不是报错。

它在 Linux 里叫什么

你拖的那条红线 = memory.max。

越线时被干掉的进程，日志里通常只有一行 OOMKilled（Out Of Memory）。而且被杀的不一定是「吃得最多的那个」——内核会挑一个它认为代价最小的，这个选择经常反直觉。

所以容器反复重启，最常见的原因不是程序有 bug，是限制设小了。

场 景 三客人要用主人的工具

一台「虚拟机」就像一个住进你家的客人：他有自己的房间、自己的东西，大部分事情在自己屋里就能做。
但有些工具只有主人有——硬盘、网卡、时钟。他每用一次，都得走出房间办一趟手续。

为什么「走出房间」这么贵

客人在自己屋里算术，用的是同一块 CPU，和真机一样快，一分钱不多花。

但只要他想碰主人的东西，就得走一整套流程：停下 → 出门 → 管家接手 → 操作 → 回家 → 继续。这一趟来回花掉的时间，够他算好几千次加法。

虚拟化「慢」，慢的全是这些来回。所以过去二十年所有的优化都在做同一件事：想办法让他少出门。把工具搬进他屋里、给他一把钥匙、开一个传递窗口——

它们在 Linux 里叫什么

「走出房间」= VM Exit，「回家」= VM Entry，中间接待他的管家 = hypervisor，在 Linux 上就是 KVM。

「给他一把钥匙」（有些事他可以自己在屋里做）= VT-x / AMD-V，CPU 直接提供的硬件虚拟化。

「把工具搬进他屋里」（不模拟真设备，双方约定怎么配合）= virtio。

「开个传递窗口」（东西直接递进去，不用他出来拿）= Posted Interrupt。

所以那篇文章为什么把票投给 KVM

KVM 本身只是 Linux 内核里的一个模块，代码量不算大。它做的事是：把 CPU 提供的虚拟化能力，包装成一套干净的接口。

真正让「云」成为可能的就是这套机制——它把「再买一台机器」变成了「再开一个客人」。你今天用的每一个云服务，底下跑的都是这些来回。

这一页的三个场景，来自你收藏的知乎回答 Linux 内核中有哪些比较牛逼的设计?（作者 海纳，赞同 924）。
那篇把票投给了四样：KVM（一票）、eBPF（一票）、cgroup 和 DRM（各半票）。 这一页覆盖了 cgroup 和 KVM。eBPF（"给程序装监控"）和 DRM（图形驱动）是另外两个故事，留着以后单独做。
